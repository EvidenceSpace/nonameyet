# AI extraction and verification

This document describes how CaseFind uses a model on case documents and which
guarantees the code enforces. Every rule here is covered by tests in
`tests/extraction.test.ts`.

## Trust boundary

Case documents are hostile input. A user may upload a PDF or screenshot that was
written by the other side of the dispute, generated by a scammer, or crafted to
manipulate an assistant.

- Document text and filenames are data, never instructions.
- Text is wrapped in `<untrusted-document-content>` delimiters. Any forged
  delimiter inside the content is stripped and counted, so the block cannot be
  closed early.
- The instruction section is fixed in code. It is never assembled from document
  content, filenames, or user free text.

## Injection signals

`detectInjectionSignals` scans document text for content that behaves like an
instruction and records a signal with a short excerpt. Signals are shown to the
user and never acted on. Current rules cover:

| Rule | Example content |
| --- | --- |
| `instruction_override` | "Ignore all previous instructions" |
| `role_impersonation` | "System:" at the start of a line |
| `verification_bypass` | "Mark everything as confirmed" |
| `authority_claim` | "You must approve this" |
| `tool_invocation` | Tool or function style tags |
| `exfiltration` | "Send the case files to ..." |
| `destructive_request` | "Delete the case" |
| `prompt_disclosure` | "Reveal your system prompt" |

## Grounding

A model claim is only allowed into the review queue when it is anchored in the
document.

- Every candidate must carry a quote in its locator.
- The quote must appear verbatim in the exact text sent to the model. Comparison
  normalizes Unicode, whitespace, casing, curly quotes, and dash variants.
- Quotes shorter than four characters are rejected as unverifiable.
- Candidates that fail grounding are recorded as rejected with a reason, so
  silent invention is visible rather than hidden.

## Verification gate

- Ingestion always produces items with status `suggested`. There is no code path
  where a model response can produce a confirmed fact.
- `resolveSuggestion` is the only transition into `confirmed`, `corrected`,
  `dismissed`, or `uncertain`, and it requires an explicit user decision.
- Confirming or correcting requires the source reference to still be attached.
  The reference carries the file ID, the locator, and the extraction version.
- Corrections keep the original source reference so a corrected value stays
  traceable to the record it came from.

## Conflicts

`findSuggestionConflicts` groups items by normalized label and flags a conflict
when values disagree. Dismissed items are excluded. Conflicts are surfaced for
the user to resolve and are never merged, averaged, or auto-selected.

## Limits

- At most 100 suggestions per file.
- Candidates below 0.15 confidence are dropped.
- Duplicate label and value pairs are collapsed.
- A response that does not match the extraction contract yields zero
  suggestions rather than a partial parse.

## Out of scope by design

The pipeline never produces legal advice, never asserts that a document is
authentic, and never predicts the outcome of a dispute. Those are product
boundaries, not model settings.
